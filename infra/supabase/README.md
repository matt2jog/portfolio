# Portfolio Supabase operations

## Target roles and ACLs

Portfolio administrator reconciliation is the ordered operation `C:\Users\matth\OneDrive\Desktop\programs\personal_brand\services\portfolio\infra\supabase\portfolio-pre-migration.sql` → digest-pinned migrations → `C:\Users\matth\OneDrive\Desktop\programs\personal_brand\services\portfolio\infra\supabase\portfolio-role-acls.sql`. The first phase opens bounded managed-administrator memberships; the final phase reconciles object ACLs, proves the exact graph, and removes those memberships. Never invoke the final file by itself after a successful run: its inability to administer owner-scoped objects without the bounded pre-phase is intentional. The complete operation is idempotent and a subsequent rerun must be a no-op. Neither SQL file contains or changes a password. Run the operation as the target Supabase database administrator after `vector` has been installed in `extensions` by `postgres`.

The three connection roles are exact `LOGIN NOINHERIT` roles without administrative attributes. Runtime and legal have no memberships. The migrator has exactly `portfolio_audit_owner` and `portfolio_compensation_operator`, each with `ADMIN FALSE`, `INHERIT FALSE`, and `SET TRUE`. Both audit roles are exact `NOLOGIN NOINHERIT` roles without administrative attributes or parent memberships. The administrator's PostgreSQL-managed role-administration edge is separate from this application membership contract.

`portfolio_migrator` owns the `portfolio` namespace and all ordinary Portfolio objects. Before audit objects exist, it temporarily receives grantable `USAGE, CREATE` only on `portfolio`, allowing migration `0016` to assign and then remove the audit roles' ownership prerequisites. The required post-migration rerun removes those grant options and leaves ordinary `USAGE, CREATE`, `USAGE` on `extensions`, and database `TEMPORARY`. The audit tables, their indexes and identity sequence, and audit trigger functions are owned by `portfolio_audit_owner`; the compensation function is owned by `portfolio_compensation_operator`. Runtime and legal have `USAGE` only on `portfolio` and `extensions`. The audit roles have non-grantable `USAGE` only on `portfolio`.

Database `TEMPORARY` inherited through `PUBLIC` is allowed for runtime/legal and is not converted into a direct grant. Shared-project `public` schema `USAGE` is tolerated, but every public relation, sequence, column, routine, and standalone type remains inaccessible. Every other non-system namespace is denied by an explicit connected-role allowlist, so a later `future_service` schema fails closed without a code change and review. Direct grants to either audit role are scrubbed there as well; switching from the migrator into an audit role does not cross the Portfolio schema boundary. Default `PUBLIC` routine/type privileges in an inaccessible sibling schema do not create effective access without schema `USAGE`.

The runtime relation matrix is deliberately table-specific:

- `SELECT`: `admin_policy_acceptance`, `ai_models`, `all_skills`, `bio`, `bio_paragraphs`, `browser_tracking`, `browser_tracking_ips`, `career_event_checkpoints`, `career_event_inbox`, `education`, `experiences`, `github_timeline_events`, `linkedin_timeline_events`, `personal_information`, `portfolio_skills`, `projects`, `skills_group`, `users`, `welcome_messages`, and `xyz_bullets`.
- `INSERT`: `admin_policy_acceptance`, `all_skills`, `audit_logs`, `browser_request_logs`, `browser_tracking`, `browser_tracking_ips`, `career_event_checkpoints`, `career_event_inbox`, `career_event_quarantine`, `education`, `experiences`, `github_timeline_events`, `ip_rate_logs`, `portfolio_skills`, `projects`, `skills_group`, `users`, `welcome_messages`, and `xyz_bullets`.
- `UPDATE`: `admin_policy_acceptance`, `all_skills`, `browser_tracking`, `browser_tracking_ips`, `career_event_checkpoints`, `career_event_inbox`, `education`, `experiences`, `portfolio_skills`, `projects`, `skills_group`, `users`, and `welcome_messages`.
- `DELETE`: `education`, `experiences`, `portfolio_skills`, `skills_group`, `welcome_messages`, and `xyz_bullets`.

Runtime has no access to `schema_migrations`, the unused legacy `session` table, `legal_document_versions`, or `legal_document_active_ranges`. It has no sequence, column-level, routine, standalone-type, `TRUNCATE`, `REFERENCES`, `TRIGGER`, or grant-option privilege. `legal_audit_writer` has only non-grantable `INSERT` on `portfolio.legal_document_versions` through the one exact insert policy; it cannot `SELECT` the table or view. `portfolio_compensation_operator` has non-grantable `SELECT, INSERT, UPDATE, DELETE` only on the 23 audited source relations, `SELECT` on mutation history and compensation payloads, and ownership of the compensation function. `portfolio_migrator` alone receives non-grantable `EXECUTE` on that function. The reconciler removes every non-owner Portfolio grant before rebuilding the complete runtime/legal/audit matrix, so an unrelated database role cannot retain table, column, sequence, routine, or type access. `PUBLIC`, `anon`, and `authenticated` have no table or column ACL on either legal object. Application routines/types default closed; only `postgres`-owned members of the `vector` extension are accepted in `extensions`. The connection search path remains `portfolio, extensions`, which leaves `pg_catalog` implicitly first.
